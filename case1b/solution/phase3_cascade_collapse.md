# 阶段三参考实现详解（`phase3_cascade_collapse.py`）

## 1. 阶段目标回顾

把同一个事故扰动作用到阶段二三段不同的运行点上，让玩家对比"高效率
=高脆弱性"的代价。事故就是早高峰里非常常见的"小型事故占用 1～9 个
路口数百步"。

## 2. 实验设置

```python
SPILL = 0.30                          # 与阶段二一致
DISSIPATION = 0.18
INFLOW = (1.0, 1.6, 2.2)              # 来自阶段二的三段
EVENT_STEP = 3000                     # 事故发生时刻（远离 warmup）
EVENT_LEN  = 600                      # 持续 600 步
EVENT_RADIUS = 1                      # 3x3 街区被冻结
```

事故由 `DisturbanceSpec` 描述。冻结期间，被波及的路口仍会接收车辆，
但**不会倾倒**——压力只能向外溢出而不能向内排出，于是事故周围的
负载会迅速堆高。

## 3. 关键统计量

- **peak_cong**：事故发生到事故清除后 200 步内，平滑后的拥堵传播范围
  的最大值（"事故让多大范围被波及"）。
- **recovery_steps**：事故清除后，拥堵传播范围回落到
  `baseline + 0.1 * (peak - baseline)` 所需步数（即"消化掉 90% 多余压力"
  所需时间）。这种相对峰值的归一化定义让不同 baseline 的三段可比。
- **thrpt_drop**：事故期间相对事故前 1000 步的吞吐量下降。

`recovery` 的 baseline 用事故前 1000 步窗口估计，target 用峰值的 10%
余量定义——既不会被超临界段较高的稳态卡死，也不会让亚临界段瞬间满足。

## 4. 实测结果（可复现）

```
regime                          peak_cong   recovery_steps   thrpt_drop
Subcritical inflow=1.0            1.33        116            0.017
Near-critical inflow=1.6          3.47         55            0.070
Supercritical inflow=2.2          4.47         54            0.039
```

读出来的故事：

- **峰值拥堵** 严格单调上升：`1.33 → 3.47 → 4.47`，越靠近超临界，事故
  让更多路口进入瓶颈状态。
- **吞吐量下降** 在 stress edge 附近最大（0.07）——网络在那里最
  "对扰动敏感"，正好说明了"临界 = 高敏感性"。
- **恢复时间** 在亚临界段反而最长（116 步）——因为亚临界段 baseline
  本就低，绝对峰值虽小，但相对而言更难掉到那么低；这反映了"安静的
  网络一旦被打乱，靠自身随机活动慢慢消化压力"的现实情况。

> 注意：这里的 recovery 用的是"相对峰值的 10%"作为终点，因此它不是
> 越短越好——更应该结合峰值 + 吞吐量惩罚一起读。
