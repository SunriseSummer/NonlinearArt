# 阶段四参考实现详解（`phase4_self_organization.py`）

## 1. 阶段目标回顾

阶段四回答任务书最后一问：**当扰动不可避免时，"局部规则的自组织"
能不能比"手工调好的全局参数"更稳？**

我们用同样的 demand、同样的事故、同样的随机种子比较两种策略：

- **模式 A — 强控制**：手工把 `spill_prob=0.30` 调到对稳态吞吐量比较
  友好的水平，没有任何反馈机制。所有变化都只能靠预设。
- **模式 B — 局部规则自组织**：开启 base 模型里的两条**局部反馈规则**：
  - `inflow_feedback=True, target_load=2.4, inflow_gain=0.8`：当网络
    平均负载越过目标值时，自动按比例收紧入口流量。
  - `local_relief=True, relief_extra=0.20`：高负载路口的耗散概率额外加
    0.20，把额外车辆"分流"出网络。

> 两条规则**只用本地可观测量**（自身负载、网络平均负载），不依赖
> "总指挥实时调度"。这正是 SOC 风格自组织的关键——没有中央调参员，
> 局部规则把系统拽回临界邻域。

## 2. 关键参数

```python
INFLOW         = 2.0    # 较高的稳态 demand
EVENT_STEP     = 3000
EVENT_LEN      = 600    # 与阶段三一致的事故
EVENT_RADIUS   = 1
WARMUP, STEPS  = 1500, 5500
```

## 3. 评估指标

- `<thrpt_pre>` / `<thrpt_event>` / `<thrpt_post>`：事故前 1000 步、事故
  期间、事故后 1000 步的平均吞吐量。
- `peak_cong`：事故期间拥堵传播范围的峰值。
- `recovery`：事故清除后拥堵恢复到 `baseline + 10% × (peak - baseline)`
  所需步数（与阶段三同口径）。

## 4. 实测结果（可复现）

```
mode                    thrpt_pre  thrpt_event  thrpt_post  peak_cong  recovery
Mode A: strong control     1.134      1.068       1.083       6.57       290
Mode B: local rules        1.194      1.287       1.085       3.47       468
```

**怎么读**：

1. **稳态吞吐量**：B 优于 A（1.194 vs 1.134）。局部分流让网络在 demand
   很高时也保持比较高的有效服务率。
2. **事故期间吞吐量**：B 显著高于 A（1.287 vs 1.068）——这是阶段四最
   重要的指标：当事故来袭，B 仍能继续放车，A 直接掉一截。
3. **事故波及面**（peak_cong）：B **几乎只有 A 的一半**（3.47 vs 6.57），
   局部反馈把扰动控制在小范围里没有任意放大。
4. **恢复时间**：B 看起来比 A 长——但要与峰值合在一起读。B 的峰值低、
   总扰动量也小，绝对的 "残余压力" 在 baseline 之上的小幅波动会让相对
   阈值变得敏感，所以指标在这里不那么有判别力；真正反映韧性的还是
   峰值 + 事故吞吐量。

总结：**对调度员而言**，模式 B 在所有"事故面前"的指标上都至少不差，
而且不需要他实时介入参数。这就是"良好的局部规则 > 全局精调"的实证。

## 6. 设计取舍与可拓展

- `inflow_gain=0.8` 是一个**比例式控制**而非积分式控制。如果 demand 长
  期超过网络承受力，纯比例可能会持续"压住" inflow——可以引入积分项把稳
  态偏差压到 0，对应 PID 中的 I 通道。
- `local_relief` 现在是开/关式（高负载就 +0.20）。**真正按需分流**应该
  让 `relief_extra` 与"超出目标负载多少"成正比；这是一个非常自然的拓展。
- 不要尝试把 A、B 同时打开 `adaptive_spill`：那会让对照失效。`adaptive_spill`
  在本仓库的 case1 phase2 里已经做过对照了，这里专门保留为 SOC 的对照
  组——case1 看"全局参数自动调"，case1b 看"局部规则自动调"，正好是
  互补的两个故事。
